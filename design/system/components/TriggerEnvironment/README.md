The trigger page's **What its jobs get**: what a job of this trigger would start with on each host it runs on, as each host's last doctor run published it, and each part a person can change, changed in place. Before it, the page listed each run field as written, beside the deployment default, and most were changed by hand in the triggers file.

**What waits.** Per-extension switches, a chip per extension tool, and the two fields behind them (`run.excludeExtensions`, `run.excludeExtensionTools`) wait on a later pull request, which holds until a release that reads a file's version is on every host. The older-host refusal and the `exclude-tool-not-loaded` refusal wait with them. Until then each extension is shown and not switched, and the row says so.

**How a person uses it.**
- **The hosts** come first: one pill per host the trigger runs on, saying whether its jobs get the same there. Here build3's overlay adds git-guard, mini1 goes without it, and mini2 has published no doctor run, so it reads unknown, never the same. "The same" needs two hosts that can say and agree on everything the rows beneath say: what `hostsAgree` compares of what reaches this trigger, and the image and its pi. A host alone reads *the only host*, or *the only one known* beside silent ones, and one with no answer for the flow says so. A host whose doctor found the flow nowhere says so too, however many hosts agree with it.
- **One row per kind,** each with its control and, under it, what its last run on one host that said what it loaded had (part 1's record), naming the host because hosts differ. Here that is mini1. Triggers names gh-e9a0 as trigger 3's last, and it was refused before its container started, so the card says why it quotes gh-9575:
  - **Model:** the provider and the model, each typed or picked from the catalog's priced models for the providers in use, because a model the overlay declares is not in the catalog and the preview judges what is typed; the job cap, which a trigger can only lower: `effectiveCostCapMicros` takes the smaller, and a value above `PI_MAX_COST_USD` refuses the file; the allowed models and the fallbacks.
  - **Flow and skills:** a skill typed or picked from what a job can find (the repository's where it is on this host, the overlay's, a staged package's), and doctor's answer on each host. A forge's repository is not on a host, so doctor cannot answer for that tier, and the card says so. Where doctor found the flow nowhere, at the repository's HEAD or in any other tier the trigger loads from, the row warns before any run has paid to show it. A run that went without its flow says so under the row, from its record, and a record cut short says that at the top.
  - **Extensions:** the all-off switch for staged packages (`"packages": false`), then each staged package and overlay extension, shown, saying where each is and what the last run had of it. The repository's own are shown too: they are merge-gated content, changed in the repository.
  - **MCP servers:** a switch per server a host publishes or the trigger names, with its transport, where it is, its exposure and the key it uses by name, and each host: which have it, which do not, in warning tone, and which are unknown. The pills compare what these jobs get, so a server the trigger does not name is on no pill, and its row says when turning it on would differ by host.
  - **Tools:** a chip per tool of pi's own, and for a server the trigger names, `mcp__<server>__*` as a whole and the five `MCP_EXCLUDABLE_TOOL_NAMES`. On means not removed. No host publishes a tool's name, so each staged or overlay extension's tools are named as a run loaded them, by its id and host, shown and not switched, and not at all once the file withholds the packages they came with; a repository's stay a count. `report_progress` is shown where the file sets `run.progress`, which brings it, and no list removes it.
  - **Image and secrets:** shown, each host's image and pi with the `PI_JOB_IMAGE` they come from, and changed where they are today (the host's env or `run.image` in the file, the Secrets page).
- **The same rows, in other states** (`p-trigger-gets-states`): allowed models and a fallback set, staged packages off, a trigger with no run in the history, a run that went without its flow, and a schedule whose repository lacks its flow, before any run has paid to show it.
- **Changes collect** in one bar (*2 changes, not written yet*) with **Preview the change** and **Discard**, a form's own reset. TriggerEnvironmentChange draws the preview, and any move of a control closes it, because its Confirm no longer says what the form says. The bar says a Confirm elsewhere on the page reloads it and drops these.

**Panels.** `p-trigger-gets`, `p-trigger-gets-how`, `p-trigger-gets-states`, beside TriggerDetail's panels.

**The server provides.**
- **The file:** the trigger's fields, read once with the digest of that entry, so what the person saw and what the stale check compares are one read; and the deployment defaults; the overlay's MCP servers (Connections); the catalog's priced models.
- **From part 1:** the last run's record, for what loaded and the names of each extension's tools.
- **For each host:** What the host's last doctor run published, with its time, or unknown. The repository's part is decided at its base commit. The publication is a new key, `doctor:loads:<name>`, holding overlay extensions and skills, staged packages, each trigger's flow tier, and each MCP server with its `enabled` state, which is what *off* reads: an ok doctor check publishes only its id and level, so the answer is not there to read. Each host's image and pi's version are not in it: they come from what every live host already publishes, `host:h:<name>` (`image`, `imageDigest`, `piVersion`, `INT-HOST-REGISTRY-CONTRACT`), so that row knows mini2 while the publication's rows do not, and a host whose row has expired reads unknown there too.
- **A person-only write** through the trigger edit's planner: a trigger's spend and reach fields (`run.models`, `run.fallbackModels`, `run.mcp`, `run.maxCostUsd`) stay out of every tool's reach. That is what "no tool" means here: `dispatch_trigger_edit` still sets flow, provider and model, and `dispatch_set` can still set the deployment's own dollar caps, each behind a Confirm (`admin/src/action-policy.mjs`).
- **On TriggerDetail,** the card's fields leave *By hand* and the Edit form stops offering flow, provider and model, so no key has two editors. Image, secrets, the skills folder and the rest stay where they are.

**Who sees what.** An operator changes it. A viewer reads the rows without controls, and the page holds no digest of the entry (TriggerEnvironmentChange). No tool reaches this action; `dispatch_trigger_edit` keeps today's scope. An agent's page draws no card.

**Why it works this way.**
- **What a job gets, not what the file says.** "packages: load" means different things on different hosts; the card says which.
- **The file says what the next job gets, and a record says what that run had.** A word from one never reads as the other: under a row the record's words are past, by its id and host.
- **Unknown, never the same.** A host with no publication, one too old or too new to read, or one whose list of what matters here is cut, proves nothing, so its pill does not say it matches. The same goes for each row the publication answers: a staged package or a server reads unknown on mini2, never "every host".
- **A blank field removes a key; an untouched one is not sent.** Keys that are not sent stay byte-identical in the file.
- **One preview for every change,** so a widening (an MCP server and its key) and its side effects (a job in line refused as `trigger-skew`) are read before anything is written. No money or policy is worked out in the browser.
- **The last run under each row,** so a setting and what it did sit together.
