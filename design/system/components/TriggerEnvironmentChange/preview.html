What it refuses, and why

  • docs is off on mini1, not on build3, and mini2 is unknown. Turning it on would refuse trigger 3’s jobs on a host without it, or with it off, as mcp-server-unknown, and on a host with no overlay or no mcp.json as mcp-config-invalid, before they spend. The switch says so before you preview.
  • A main model that cannot make one call under the cap. anthropic/claude-opus-5-5 needs at least $2.654295 for a short task’s first call, above the deployment’s $2.00 job cap, so the runner would refuse every call to it before it is sent. A trigger can only lower the deployment’s job cap: choose another model. The deployment’s own cap belongs to its settings, not to this page.
  • A cap that clears the floor but not a short task. It previews, and says so: anthropic/claude-opus-5-5 clears this $2.62144 job cap only for the smallest first call: a short task’s needs $2.654295, so most jobs that call it would be refused before they spend. Choose another model, or a job cap of at least $2.654295; a repository’s context files and a longer task need more.
  • A server whose key this host does not hold. It previews, warns, and can still be confirmed, since another host may hold it: On this host this trigger’s jobs would be refused as mcp-secret-unmapped, before they spend. run.secrets is set in the triggers file, not on this page. This reads this host’s .env and overlay; what the worker’s own service environment sets cannot be seen from here.
  • A hand-written file. It previews, and says so: This file is not in the writer’s layout, so this write also rewrites all of it: spacing and line breaks move in lines this change does not touch, and what each key says does not. Undo puts the values back, not that layout.
  • A job cap above the deployment’s. A trigger’s job cap can only lower the deployment’s, and a value above PI_MAX_COST_USD refuses the whole file when a worker loads it.
  • This trigger changed since the page drew it. Nothing was changed. Reload the page and make the change again: nothing is written over an edit you have not seen.
  • A host on an older release. Either exclusion needs the file at version 2, so it is refused while a live host reads less, publishes no version, or cannot be read: such a host drops a key it does not know, which for a narrowing runs its jobs wider on a clean record. The preview says when it stamps the file, and when a change takes the stamp off.
  • A name on no host. No live host holds pi-linter, as each one’s last doctor run published it, so leaving it out would keep nothing out. Check the name, or run pi-dispatch doctor on the host that has it. Where a host cannot say, the preview warns instead.
  • A tool chip off. It previews, and says what a job does if the name matches nothing: A job that reaches its container with nothing held back from it, no parent job and every extension loaded stops before its prompt as exclude-tool-not-loaded if no extension registered lint_file when it loaded. On a trigger that holds extensions back it says instead that the job runs, and its log and record name it.
  • A package a job needs. It previews, and says so: a flow doctor found only in that package, a subscription connection’s adapter (auth-adapter-disabled), a schedule’s canary of that package (package-canary-excluded).
  • Every way to a server removed. On every host this trigger’s jobs would be refused as mcp-excluded, before they spend. Remove the server from run.mcp, or keep a tool that reaches it out of run.excludeTools. Where only this host’s overlay leaves it no way in, the preview warns instead: another host’s overlay may route it another way.
  • Not here, by design: the repository’s own extensions (change the repository), a new extension or version (Updates), secrets (Secrets), the image (each host’s env, or the file) and the skills folder (the file).
